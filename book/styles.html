Chapter 4

Making the Interface Look Like an App

At the moment, if you open index.html in the browser, it looks rather weird. The HTML structure is already there, but the browser is showing the elements using their default appearance. The buttons look like ordinary browser buttons, the sections have no spacing or layout, and the modal has no proper visual presentation. The next step is to add CSS and completely change the way the interface looks.

CSS stands for Cascading Style Sheets. HTML describes what elements exist on the page, while CSS describes how those elements should look and how they should be arranged. In our project, HTML gives us the structure of the greeting-card application, and CSS turns that structure into something that looks much more like a mobile application.

Adding the Style Tag

In previous chapter, we deliberately left the <style> element empty. Now we are going to put our complete CSS inside it. The <style> element belongs inside the <head> section of index.html.

Our document should therefore contain a structure like this:

<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Greeting Cards</title>
    
    <style>
        /* Our CSS will be here */
    </style>
</head>

We are not creating a separate CSS file for this project. Everything stays inside index.html. This keeps the application simple and makes the entire interface available in one file.

How CSS Rules Work

Before looking at every rule, it is useful to understand the basic structure of CSS. A CSS rule normally consists of a selector followed by one or more declarations.

.card {
    background: white;
    border-radius: 16px;
}

The .card part is the selector. It tells the browser which HTML elements should receive the styles. The declarations inside the curly braces describe what should change. Here, every element with the class card gets a white background and rounded corners.

A selector beginning with a dot refers to a class. A selector beginning with # refers to an element with a particular ID. A selector such as body refers directly to an HTML element.

First Rule: Box Sizing

* {
    box-sizing: border-box;
}

The * selector means every element on the page. We are therefore applying box-sizing: border-box to everything.

This is one of the most useful defaults in modern CSS. Normally, an element's declared width describes its content area, and padding and borders can be added outside that width. With border-box, the declared width includes the content, padding, and border.

For example, if an element has width: 100% and padding: 20px, border-box prevents the padding from unexpectedly making the element wider than its available space. This is especially important on mobile screens, where horizontal space is limited.

Removing the Browser's Default Spacing

html,
body {
    margin: 0;
    padding: 0;
}

Browsers apply default margins and other spacing to some HTML elements. For an application interface, we usually want to control the spacing ourselves.

Setting margin: 0 and padding: 0 removes the default outer and inner spacing from the page itself. We can then add exactly the spacing we need later.

Styling the Body

body {
    background: #f3f3f3;
    font-family: Arial, sans-serif;
}

The body contains everything the user sees on the page. We give it a very light gray background using the hexadecimal color #f3f3f3.

We also specify the font. The application uses Arial when it is available. The sans-serif part is a fallback. If Arial is not available on the device, the browser chooses another sans-serif font.

This is another useful principle for mobile-first applications: do not assume that every device has exactly the same fonts. Always provide a reasonable fallback.

What Does Mobile-First Mean?

Our application is designed primarily for phones. This is what we mean by a mobile-first approach.

A phone usually has much less horizontal space than a desktop monitor. Instead of designing a large desktop interface first and trying to squeeze it onto a phone later, we start with the smaller screen and make every element fit naturally.

This affects many decisions in our CSS. Buttons are large enough to tap with a finger. Cards use the available screen width. Categories can be scrolled horizontally instead of being forced into a narrow row. The modal occupies the full width of the phone and behaves like a bottom sheet.

Mobile-first does not mean that the application can only work on phones. A responsive browser automatically scales and lays out the page according to the available space. Our starting point is simply the smallest and most constrained screen.

The Sticky Controls

.sticky-controls {
    position: sticky;
    top: 0;
    z-index: 100;
    background: white;
    padding-top: 8px;
    box-shadow: 0 2px 6px rgba(0, 0, 0, 0.12);
}

The .sticky-controls element contains the main controls of our application: the random-card button and the category buttons.

The important property here is position: sticky. It allows the element to behave normally while the page is at the top, but when the user scrolls, the element stays attached to the top of the viewport.

top: 0 tells the browser that the element should stick to the top edge of the screen.

The z-index: 100 places this element above other content when elements overlap. Without a sufficiently high stacking order, cards or other page elements could visually appear above the controls.

The white background is important because the controls remain visible while the user scrolls over the greeting cards. The shadow gives the fixed area a visual separation from the content below it.

The Category Row

#categories {
    display: flex;
    overflow-x: auto;
    gap: 10px;
    padding: 12px;
    background: white;
    position: static;
    scrollbar-width: none;
    -webkit-overflow-scrolling: touch;
}

The categories are placed inside a horizontal scrolling container. This is particularly useful on a phone because we may have many categories, and displaying all of them at once would make the interface too narrow.

display: flex places the category buttons next to each other in a row.

overflow-x: auto allows horizontal scrolling when the buttons are wider than the available screen.

The gap: 10px creates ten pixels of space between the buttons. The padding: 12px adds space around the entire category area.

scrollbar-width: none hides the scrollbar in browsers that support this property. The following rule handles WebKit-based browsers:

#categories::-webkit-scrollbar {
    display: none;
}

The scrollbar still exists functionally; we are simply hiding its visual representation. Users can still swipe the category row horizontally on a phone.

The -webkit-overflow-scrolling: touch property was commonly used to improve scrolling behavior on older iOS browsers. Modern browsers handle scrolling much better automatically, but keeping the property is harmless for this simple project.

Category Buttons

.category-btn {
    flex-shrink: 0;
    border: none;
    background: #4f46e5;
    color: white;
    padding: 12px 18px;
    border-radius: 999px;
    white-space: nowrap;
    font-size: 16px;
    cursor: pointer;
}

These rules style every category button that our JavaScript creates.

flex-shrink: 0 is particularly important here. Because the buttons are inside a flex container, the browser could otherwise try to shrink them to make everything fit on one line. We do not want that. Each button should keep its natural width, and the user should scroll horizontally instead.

border: none removes the browser's default button border.

background: #4f46e5 gives the button its purple-blue background, while color: white makes the text readable against it.

The padding gives the button enough physical size to be comfortably tapped with a finger. This is an important mobile-first consideration: a button should not be so small that users have difficulty touching it accurately.

border-radius: 999px produces a pill-shaped button. The exact number is not important. A very large radius simply makes the corners fully rounded.

white-space: nowrap prevents a category name from wrapping onto multiple lines. Each category therefore remains one compact button.

The :active rule provides a small visual response when the user presses the button.

.category-btn:active {
    transform: scale(0.98);
}

The button becomes slightly smaller while it is being pressed. This gives the interface a small amount of physical feedback.

The Random Button

#randomBtn {
    display: block;
    width: calc(100% - 20px);
    margin: 0 auto;
    padding: 14px;
    border: none;
    border-radius: 14px;
    background: #222;
    color: white;
    font-size: 16px;
    font-weight: bold;
    cursor: pointer;
}

The random button is intentionally large. On a phone, a large full-width control is easier to understand and tap.

width: calc(100% - 20px) makes the button almost as wide as its parent, leaving ten pixels of space on each side. The calc() function allows CSS to perform this simple calculation directly.

margin: 0 auto centers the button horizontally. Since the available width is smaller than the parent, the automatic left and right margins distribute the remaining space evenly.

The button uses a dark background and bold text so that it is visually different from the category buttons.

It also receives the same small press effect:

#randomBtn:active {
    transform: scale(0.98);
}

The Cards Container

#cards {
    padding: 10px;
    display: grid;
    gap: 12px;
}

The #cards section is currently empty in our HTML. JavaScript will later create the actual greeting cards inside it.

We use CSS Grid with display: grid. At this stage we are deliberately keeping the layout simple: one column on the small screen. The cards will naturally occupy the available width.

The gap: 12px creates consistent vertical and horizontal spacing between cards.

This is a good example of mobile-first design. We do not need complicated multi-column rules just to make the first version work on a phone. The simplest layout is usually the most useful starting point.

The Card

.card {
    background: white;
    border-radius: 16px;
    overflow: hidden;
    box-shadow: 0 2px 8px rgba(0, 0, 0, 0.1);
}

Every greeting card displayed by JavaScript will receive the card class.

The white background separates the card from the light gray page background. The rounded corners make the card look more like a modern mobile interface component.

overflow: hidden is important because the image inside the card may reach the edges of the card. It ensures that content does not visually escape through the rounded corners.

The box-shadow creates a subtle shadow underneath the card. The result is a visual separation between the card and the page without requiring a visible border.

Card Images

.card img {
    width: 100%;
    display: block;
}

The greeting-card image should use the full width of the card. Therefore, we set its width to 100%.

display: block removes the small inline-image behavior that can otherwise leave unwanted space underneath an image. It also makes the image behave more predictably inside the card.

Card Titles

.card-title {
    padding: 10px;
    font-size: 14px;
}

The title appears below the image. The padding gives the text some breathing room, while the smaller font size keeps the title visually secondary to the greeting-card image.

The Modal

#modal {
    position: fixed;
    inset: 0;
    background: rgba(0, 0, 0, 0.7);
    display: flex;
    align-items: end;
}

The modal is the full-screen layer that appears when the user opens a greeting card.

position: fixed attaches the modal to the browser viewport rather than to the normal document flow. It therefore stays in place even if the underlying page has been scrolled.

inset: 0 is a convenient shorthand for setting top, right, bottom, and left all to zero. In other words, the modal covers the entire screen.

The background uses rgba(). The first three values represent red, green, and blue, while the fourth value is the alpha channel, which controls transparency. A value of 0.7 makes the black background partially transparent, so the page underneath is darkened rather than completely hidden.

The modal uses Flexbox with display: flex. The align-items: end rule places the modal content at the bottom of the screen. This gives us a bottom-sheet style interface that works naturally on mobile devices.

Hiding Elements

.hidden {
    display: none !important;
}

The modal initially has the hidden class. This rule completely removes it from the visual page until JavaScript removes that class.

The !important makes sure this rule wins over other display declarations that may apply to the same element. Without it, the modal's display: flex rule could otherwise make the element visible again.

This is a simple example of CSS and JavaScript working together. CSS defines what the hidden state looks like, while JavaScript controls when the element enters or leaves that state.

The Modal Content

.modal-content {
    width: 100%;
    background: white;
    padding: 20px;
    border-radius: 20px 20px 0 0;
}

The modal content occupies the full available width. Its white background creates the actual bottom sheet that the user interacts with.

The four values in border-radius correspond to the top-left, top-right, bottom-right, and bottom-left corners. We therefore round only the two top corners.

This makes the modal look as though a panel is sliding upward from the bottom of the phone screen.

The Modal Image

.modal-content img {
    width: 100%;
    border-radius: 12px;
}

The selected greeting-card image again uses the full width of its container. The rounded corners match the visual style of the rest of the application.

Modal Buttons

.modal-content button {
    width: 100%;

    margin-top: 10px;
    border: none;
    border-radius: 12px;
    background: #4f46e5;
    color: white;
    font-size: 16px;
    cursor: pointer;
}

The share, copy, and close buttons all receive the same styling. They are full-width controls, which makes them easy to tap on a phone.

The vertical padding makes the buttons physically larger, while the margin separates one button from the next. The rounded corners and color match the category buttons so that the interface feels consistent.

Why Are the Buttons So Large?

On a desktop computer, a mouse pointer can accurately click a small button. On a phone, the user is usually tapping with a finger. A tiny target is therefore much harder to use.

For this reason, mobile interfaces generally benefit from sufficiently large touch targets, comfortable spacing, and controls that are easy to recognize without precise pointing.

Our CSS uses padding and full-width buttons to achieve this without requiring complicated calculations or device-specific code.

Why Do We Use IDs and Classes?

Notice that our CSS uses both selectors such as #randomBtn and selectors such as .category-btn.

The # selector targets one specific element by its ID. We use this for elements such as the random button, cards container, and modal.

The . selector targets a class. We use classes when many elements can share the same appearance. Every category button can therefore use category-btn, and every generated greeting card can use card.

This distinction will become particularly important when we start writing JavaScript. The IDs give JavaScript direct access to important elements, while classes allow CSS to style groups of generated elements consistently.

CSS and JavaScript Are Separate Responsibilities

One useful principle in this project is that CSS should generally describe appearance, while JavaScript should control behavior.

For example, JavaScript will eventually create a category button and assign it the category-btn class. JavaScript does not need to know that the button should be purple, rounded, or padded. CSS already knows that because of the class.

Similarly, JavaScript will add or remove the hidden class from the modal. JavaScript does not need to manipulate every visual property of the modal. CSS handles the visual states.

This separation makes the application easier to understand and maintain. If we later decide to change the color of every category button, we only need to change the CSS rule instead of changing the JavaScript that creates the buttons.

Why We Put All CSS in One File

In a larger application, CSS is often stored in one or more separate files. For our project, however, keeping the CSS inside index.html has several advantages.

First, there are fewer files to manage. Second, the entire interface is contained in one source file. Third, the service worker can cache the application shell without having to manage a separate stylesheet dependency.

This approach is especially convenient for a beginner project where the goal is to understand how the pieces work together rather than introduce a large project structure.

Important: The CSS above is written for a mobile-first interface. We are starting with the phone layout instead of trying to build a desktop layout and then squeeze it onto a small screen. Later, if the project needs a more elaborate desktop presentation, media queries can be added without changing the basic mobile structure.

What Has Changed?

If you reload index.html now, the page should look very different from the raw HTML version. The controls have spacing and colors, the random button is large and easy to tap, the category area is prepared for horizontal scrolling, and the modal has the appearance of a mobile bottom sheet.

However, there is an important detail: the application is still empty.

The CSS has completely changed the appearance of the interface, but CSS does not create greeting cards. Our #cards section is still empty because we have not written the JavaScript that loads the CSV dataset and generates the cards yet.

So now the application looks much more like a real mobile app: it is filled with styles, spacing, colors, buttons, cards, and a modal design, but there is still no greeting-card data being loaded. In the next step, we will give the application something to actually work with.
