Chapter 7

Turning the Website into a Mobile Application

At this point, we have a working website that has been designed with mobile screens in mind. It is important to understand that mobile-friendly design and a mobile application are not the same thing. So far, our project is still simply a website. We have optimized its layout for touch screens and narrow displays, but the browser still treats it as an ordinary web page.

In this chapter, we will take the next step and turn the website into a Progressive Web App, or PWA. A PWA can still be opened like a normal website, but the browser can also provide an installable, application-like experience. We will add a web app manifest, application icons, and a service worker that can cache the application files.

Testing the Website on a Mobile Device

Before turning the website into a PWA, it is useful to test what we already have on an actual smartphone. A responsive website should be tested on a real mobile screen whenever possible, because a desktop browser window cannot reproduce every detail of a touch device.

There is one important requirement when testing the local development version on a smartphone: the computer and smartphone need to be connected to the same local network.

Start the development server from the project directory as usual:

python -m http.server

The computer will normally show an address such as http://localhost:8000. The word localhost, however, means "this device". On the smartphone, localhost would refer to the smartphone itself, not the computer running our server.

Instead, we need to use the computer's local network IP address. For example, if the computer has the address 192.168.1.25, the smartphone can open:

http://192.168.1.25:8000

The exact IP address will be different on every network. On Windows, it can be found with:

ipconfig

Look for the IPv4 address of the network connection being used by the computer.

If the smartphone cannot connect, the computer's firewall may be blocking incoming connections to the Python server. The phone and computer must also be connected to the same network, and some public or guest Wi-Fi networks deliberately prevent devices from communicating with each other.

Testing Mobile Layout Without a Smartphone

Fortunately, we do not need a smartphone every time we want to check the mobile layout. Chrome DevTools has a feature that can emulate many common mobile screen sizes directly inside the desktop browser.

Open the application in Chrome and open Developer Tools. One way to do this is to press F12. You can also right-click the page and choose Inspect.

In DevTools, look for the device toolbar button. It is usually represented by an icon showing a phone and tablet. You can also enable the device toolbar with the keyboard shortcut:

Ctrl + Shift + M

Once enabled, Chrome changes the page into a simulated mobile viewport. A device selector appears at the top of the page, allowing us to choose common devices and screen sizes.

This is generally the preferred way to develop the interface because it is fast and convenient. We can change the screen size, rotate the simulated device, inspect elements, and immediately modify our HTML or CSS without repeatedly moving between the computer and a physical phone.

However, device emulation is still an approximation. A real smartphone can behave differently because of its operating system, browser version, touch input, screen density, permissions, sharing capabilities, and other device-specific features. It is therefore useful to use DevTools throughout development and perform some final tests on a real phone when one is available.

From Mobile Website to PWA

Our application already has several characteristics that make it suitable for a PWA: it uses a responsive interface, it is served over HTTP during development, and it consists of static HTML, CSS, JavaScript, and data files.

To make it installable and give it application-like behavior, we need to provide the browser with some additional information.

The first part is the web app manifest.

Adding the PWA Information to index.html

We begin by adding several elements to the <head> section of index.html.

<link rel="manifest" href="manifest.json">
<meta name="theme-color" content="#ffffff">
<meta name="mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-status-bar-style" content="default">

The first line tells the browser where our web app manifest is located.

<link rel="manifest" href="manifest.json">

The manifest is a separate JSON file that describes the application. It contains information such as its name, icon files, starting URL, colors, orientation, and how the browser should display it when installed.

The theme-color value tells the browser which color to use for parts of the browser interface associated with the application.

The mobile web app meta tags provide additional information for mobile browsers, including browser-specific behavior related to running the site in an application-like mode.

Creating manifest.json

Next, create a file named manifest.json in the project root, next to index.html.

{
    "name": "Greeting Cards",
    "short_name": "Greeting Cards",
    "description": "Greeting cards for every day",
    "start_url": "./",
    "display": "standalone",
    "background_color": "#f3f3f3",
    "theme_color": "#ffffff",
    "orientation": "portrait",
    "icons": [
        {
            "src": "icons/icon-192.png",
            "sizes": "192x192",
            "type": "image/png"
        },
        {
            "src": "icons/icon-512.png",
            "sizes": "512x512",
            "type": "image/png"
        }
    ]
}

The original application uses Russian values in this file. The book shows the translated English version, just as we did with the visible HTML interface. The purpose of the values is the same.

name is the full application name. It can be displayed when the application is installed.

short_name is a shorter version of the name that can be used when there is limited space, such as under an application icon.

description provides a short description of the application.

start_url tells the browser which URL should be opened when the installed application starts. Here, ./ means the application's own root location.

The display property is particularly important:

"display": "standalone"

This asks the browser to open the application in an application-like window rather than displaying the normal browser interface around the page.

background_color defines a background color that can be used while the application is starting. theme_color describes the application's theme color.

The orientation property requests portrait orientation. This makes sense for our greeting-card application because the interface was designed primarily for vertical mobile screens.

Application Icons

The manifest also specifies two PNG icons.

"icons": [
    {
        "src": "icons/icon-192.png",
        "sizes": "192x192",
        "type": "image/png"
    },
    {
        "src": "icons/icon-512.png",
        "sizes": "512x512",
        "type": "image/png"
    }
]

These files should be placed in an icons directory:

icons/
    icon-192.png
    icon-512.png

The two sizes give browsers suitable images for different installation and display situations.

Creating the Icons from an SVG

If we do not already have PNG icons, one convenient approach is to find or create an SVG image and convert it into PNG files.

SVG stands for Scalable Vector Graphics. Unlike a normal bitmap image, an SVG describes the image using shapes and paths, so it can be resized without the same type of pixelation that can occur with a small raster image.

For a simple application icon, we can find an SVG icon from a free icon website or another source that permits its use. Always check the site's license and the license of the individual icon before using it in a published application.

After downloading the SVG file, it can be converted to PNG using a free online image-conversion tool. Many websites provide this functionality: upload the SVG, choose PNG as the output format, and select the required dimensions.

For our application, create one PNG at 192 × 192 pixels and another at 512 × 512 pixels.

After downloading the converted files, rename them to:

icon-192.png
icon-512.png

Then place both files in the icons directory.

When downloading an icon from the internet, "free to download" does not automatically mean "free to use in any project". Check the icon's license before publishing the application.

The Project Structure

After adding the manifest and icons, the project now has a structure similar to this:

index.html
manifest.json
sw.js
data/
    greetcards.py
    greetcards.csv
icons/
    icon-192.png
    icon-512.png

The Python scraper remains a development/build-time tool. The browser does not run greetcards.py. It only loads the generated CSV file.

Adding the Service Worker

The next important PWA component is a service worker. A service worker is a JavaScript file that the browser can run separately from the web page and use to intercept certain network requests.

We will create a file named sw.js in the project root.

Before the browser can use it, we need to register it from index.html.

<script>
    if ("serviceWorker" in navigator) {
        window.addEventListener("load", () => {
            navigator.serviceWorker.register("./sw.js")
                .then(() => console.log("PWA service worker registered"))
                .catch(error => console.error("PWA error:", error));
        });
    }
</script>

The first condition checks whether the browser supports service workers.

if ("serviceWorker" in navigator)

The registration happens after the page has finished loading. The browser is told that the service worker file is sw.js.

If registration succeeds, a message is printed to the browser console. If something goes wrong, the error is printed instead.

Creating sw.js

Now create the sw.js file.

const CACHE_NAME = "greetcards-v1";

const FILES_TO_CACHE = [
    "./",
    "./index.html",
    "./manifest.json",
    "./data/greetcards.csv"
];

self.addEventListener("install", event => {
    event.waitUntil(
        caches.open(CACHE_NAME).then(cache => {
            return cache.addAll(FILES_TO_CACHE);
        })
    );

    self.skipWaiting();
});

self.addEventListener("activate", event => {
    event.waitUntil(
        caches.keys().then(keys => {
            return Promise.all(
                keys
                    .filter(key => key !== CACHE_NAME)
                    .map(key => caches.delete(key))
            );
        })
    );

    self.clients.claim();
});

self.addEventListener("fetch", event => {
    event.respondWith(
        caches.match(event.request).then(cached => {
            return cached || fetch(event.request);
        })
    );
});

Understanding the Cache Name

The first line defines the name of our cache.

const CACHE_NAME = "greetcards-v1";

The v1 is a version number. When we make a future change to the files being cached, we can change this name to something such as greetcards-v2. The service worker can then recognize the new cache as a different version.

Choosing What to Cache

The files we want to cache are listed in FILES_TO_CACHE.

const FILES_TO_CACHE = [
    "./",
    "./index.html",
    "./manifest.json",
    "./data/greetcards.csv"
];

These are the essential files required for the application itself: the page, the manifest, and the greeting-card dataset.

Notice what is not included: the greeting-card images.

The CSV contains URLs pointing to images hosted elsewhere. Our service worker does not download the entire collection of greeting-card images and put them into our application cache. The browser requests those images from their original online URLs when they are needed.

The Install Event

The service worker receives an install event when the browser installs a new version of the worker.

self.addEventListener("install", event => {
    event.waitUntil(
        caches.open(CACHE_NAME).then(cache => {
            return cache.addAll(FILES_TO_CACHE);
        })
    );

    self.skipWaiting();
});

caches.open() opens or creates the named cache. Then cache.addAll() requests every file in our list and stores the successful responses in the cache.

event.waitUntil() tells the browser that the installation work is still in progress and should not be considered complete until the promise finishes.

self.skipWaiting() asks the newly installed service worker to move toward activation without unnecessarily waiting for older worker instances to disappear.

The Activate Event

After installation, the service worker can become active.

self.addEventListener("activate", event => {
    event.waitUntil(
        caches.keys().then(keys => {
            return Promise.all(
                keys
                    .filter(key => key !== CACHE_NAME)
                    .map(key => caches.delete(key))
            );
        })
    );

    self.clients.claim();
});

The code obtains the names of all available caches and removes every cache whose name does not match the current CACHE_NAME.

This is useful when we update the application from greetcards-v1 to greetcards-v2. The old cache can be removed instead of remaining on the user's device forever.

self.clients.claim() allows the active service worker to take control of pages within its scope without waiting for another navigation.

Intercepting Network Requests

The final part of the service worker handles fetch requests.

self.addEventListener("fetch", event => {
    event.respondWith(
        caches.match(event.request).then(cached => {
            return cached || fetch(event.request);
        })
    );
});

Every time the page makes a request, the service worker can check whether the requested resource is already in the cache.

If it finds a cached response, that response is returned.

return cached

If there is no cached response, the browser performs the normal network request.

return cached || fetch(event.request)

This creates a simple cache-first strategy for the files handled by the service worker.

What the PWA Adds

We now have several new pieces working together. The manifest tells the browser what the application is called, which icons belong to it, where it starts, and how it should be displayed. The service worker gives the browser a mechanism for caching the application shell and dataset. The registration code connects the service worker to our web page.

The result is still the same HTML, CSS, and JavaScript application we built in the previous chapters. We have not replaced the website with a native Android or iOS application. Instead, we have added web platform features that allow the browser to treat the site more like an installed application.

The service worker does not magically make every resource offline. In this project, we deliberately cache the application files and CSV dataset, while greeting-card images remain external resources. If an image URL is unavailable, caching the application itself does not guarantee that the image will still be available.

Testing the PWA

Because service workers and installation features are security-sensitive browser APIs, the application should be tested through a proper web origin rather than by opening index.html directly as a file:// URL.

During development, continue using:

python -m http.server

Open the application at http://localhost:8000 and use Chrome DevTools to inspect the application and service worker status.

For final PWA testing, deploy the project to GitHub Pages. GitHub Pages provides an HTTPS web address, which is important for the browser features used by a PWA.

Once deployed, test the application on a real smartphone if possible. This allows us to verify not only the responsive layout but also the installation experience, application icon, native sharing behavior, and other mobile-specific browser features.

Website, Mobile Website, and PWA

It is useful to keep the terminology clear. A normal website can be opened in a browser on many devices. A mobile-friendly website is still a website, but its layout and controls are designed to work well on small screens. A PWA adds web platform features such as a manifest, installation-related metadata, and a service worker.

Our project started as a normal static website, was designed mobile-first, and is now being extended into a PWA.

This separation is useful when developing the application because each stage can be tested independently. First we make the website work. Then we make it comfortable to use on a mobile screen. Finally, we add the PWA features that make it possible to provide a more application-like experience.
