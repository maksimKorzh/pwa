Chapter 8

Installing and Updating the PWA

In the previous chapter, we added the manifest and service worker that turn our mobile-friendly website into a Progressive Web App. The application can now be installed on a mobile device and can use cached application files.

This chapter focuses on what happens after the PWA has been created: how to install it on Android and iPhone, and how to deal with updates once the application is installed.

Installing the PWA on Android

Once the application is deployed to a public HTTPS address, an Android browser such as Chrome can offer an installation option when the site meets the browser's PWA requirements.

Open the deployed application in Chrome. Depending on the browser version and the state of the application, Chrome may show an install prompt or an option such as Install app in the browser menu.

Choose the installation option and confirm it. Android then creates an application entry using the name and icon provided by the web app manifest.

After installation, the application can be launched from the Android Home Screen or application list. Because the manifest specifies "display": "standalone", the application can open without the normal browser interface surrounding the page.

The exact wording and location of the installation command can vary between Android versions, browsers, and browser updates. If an automatic install prompt is not shown, look in the browser's menu for an installation option.

Installing the PWA on iPhone

On iPhone and iPad, the installation process is handled through Safari. Open the deployed HTTPS application in Safari and use the Share button.

In the sharing menu, choose Add to Home Screen. Confirm the name and add the application to the Home Screen.

The new icon can then be opened like other Home Screen applications. The browser uses the web app manifest and the page's PWA configuration to determine how the installed web application should behave.

As with Android, the exact interface can change between operating-system and browser versions. The important idea is that installation does not download a traditional native Android or iOS application from an app store. The browser creates a Home Screen application entry for the web application.

Updating an Installed PWA

There is an important difference between developing a normal website and developing an installed PWA: once the service worker starts caching files, refreshing the page is no longer always enough to see every change immediately.

For a normal website, we can edit index.html, reload the page, and usually see the new version immediately. With our service worker, some files may instead be returned from the cache.

For example, suppose we originally installed version 1 of the application. The service worker cached:

index.html
manifest.json
data/greetcards.csv

Later, we modify index.html and upload the new version to GitHub Pages. If the service worker continues returning the cached copy of index.html, simply reloading the installed application may still show the older version.

This is one of the most important things to understand when developing a service-worker-based application: the installed application has its own cached copy of some resources.

Changing the Cache Version

Our service worker already contains a mechanism for dealing with updated application files. We can change:

const CACHE_NAME = "greetcards-v1";

to:

const CACHE_NAME = "greetcards-v2";

When the browser detects the changed service worker, it can install the new worker and create the new cache. During activation, our code deletes caches whose names no longer match the current cache name.

This is why the cache version is useful. It gives us a simple way to tell the service worker that the set of application files has changed.

For development, however, there can still be situations where an installed application continues using an older service worker or cached resources. When testing updates, it is therefore useful to know how to manually clear the stored application data.

Clearing the PWA Cache

If an installed PWA appears to be stuck on an old version, one troubleshooting method is to clear the site's stored data or cache in the browser settings.

The exact steps depend on the operating system and browser, but the general process is to find the application's site data or storage settings and remove the stored data for that website. This can force the browser to obtain the application files again.

On a desktop Chrome installation used for development, DevTools also provides tools for inspecting service workers and clearing stored data. Open DevTools and use the Application panel. The Storage area provides controls for clearing site data, while the Service Workers section lets us inspect the registered service worker.

After clearing the site's stored data, reopen the application. The browser can then download the current application files and create the cache again.

Reinstalling the Application

Another straightforward solution on a phone is to remove the installed PWA and install it again from the current website.

This is especially useful while developing the application because it gives us a clean installation state. The browser no longer has the old installed application's stored data associated with that installation, so the current deployed files can be loaded again.

In other words, during development we have three useful update techniques:

1. Update the service worker cache version.
2. Clear the application's stored site data/cache.
3. Remove and reinstall the PWA.

Do not assume that pressing Reload in an installed PWA always means "download every file again". The service worker can intercept requests and return cached responses. This is one of the benefits of a PWA, but it also means that developers need to think about cache updates.

Why Caching Is Useful

It may seem inconvenient that cached files can hide a newly uploaded version, but caching is one of the features that makes a PWA useful.

Once essential files are stored locally, the application can sometimes load those files without downloading them again from the server. This can make startup faster and can allow parts of the application to continue working when the network is unavailable.

The trade-off is that the browser needs a way to determine when the cached version should be replaced. Our CACHE_NAME versioning system provides a simple solution for this project.
