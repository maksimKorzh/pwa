Chapter 5

Develompent HTTP Server

At this point, we have an index.html file with HTML and CSS in it and we also have a CSV dataset. It might seem that we can simply double-click index.html and start developing the application.

However, there is an important difference between opening an HTML file directly from the computer and opening it through a web server. Our application will use JavaScript to load data/greetcards.csv, and browsers apply security rules to requests made by JavaScript. If we simply open index.html from the file system, the CSV request will not work correctly in the normal way we need.

For this reason, during development we will run a small local HTTP server. The server will make our project behave much more like a real website while we are still working on our own computer.

Opening index.html Directly

If we double-click index.html, the browser opens it using a file:// URL.

Instead of something like:

http://localhost:8000/index.html

the browser will show a location similar to:

file:///C:/path/to/project/index.html

This means that the browser is reading the HTML file directly from the local file system rather than receiving it from an HTTP server.

For a completely static HTML page, this can sometimes appear to work perfectly. The browser can read the HTML, apply the CSS, and execute JavaScript that does not require network requests.

Our application, however, is going to load the CSV dataset using JavaScript. That changes the situation.

Our JavaScript Needs to Fetch the CSV

Later in the application, we will use code similar to this:

async function loadCSV() {
    const response = await fetch("data/greetcards.csv");
    const text = await response.text();

    // Process CSV data...
}

The important part is fetch().

The browser is being asked to make an HTTP request for:

data/greetcards.csv

This works naturally when the application itself is being served over HTTP or HTTPS. The browser knows that the application came from a web server and can resolve the relative URL against that server.

When the page is opened using file://, there is no web server involved. The browser is dealing with a local file instead of a normal web origin, and requests made with fetch() are subject to browser security restrictions.

Why Does the Browser Care?

Modern browsers are designed to protect users from malicious web pages.

Imagine that any HTML file on your computer could freely use JavaScript to read arbitrary files from your hard drive. A web page could potentially try to access private documents, configuration files, saved information, or other sensitive data.

Browsers therefore enforce security boundaries around web pages. One of the concepts involved is the origin.

An origin is broadly determined by the protocol, host, and port from which a resource is served. For example:

http://localhost:8000
https://example.com
https://example.org

These are different origins.

A page loaded from file:// does not behave like a normal web page served from an HTTP origin. This is one of the reasons why developing a JavaScript application by simply double-clicking the HTML file can produce confusing errors.

The Solution: A Local HTTP Server

Fortunately, we do not need a complicated server or a backend framework.

Our application consists of static files, so all we need during development is a simple static HTTP server.

Because Python is already being used for our scraping script, we can use Python's built-in HTTP server.

There is no need to install another package for this.

Python's Built-In HTTP Server

Python includes a module called http.server. It can serve files from a directory over HTTP.

Open a terminal in the root directory of the project, where index.html is located, and run:

python -m http.server

Python will start a small development web server.

By default, the server listens on port 8000.

You should see output similar to:

Serving HTTP on :: port 8000 (http://[::]:8000/) ...

The exact message can differ slightly depending on the operating system and Python version, but the important part is that the server is running on port 8000.

Opening the Application Through the Server

Now open a browser and go to:

http://localhost:8000

You can also explicitly open:

http://localhost:8000/index.html

The browser is now receiving the application from a local HTTP server rather than reading the HTML directly from the file system.

The address localhost means your own computer. It does not refer to a remote website.

The port 8000 identifies the particular network service that Python started.

What Does localhost Mean?

localhost is a special hostname that refers back to the computer you are currently using.

When you open:

http://localhost:8000

you are not connecting to the public internet to find your application. Your browser is connecting to the Python server running locally on your own computer.

The complete flow looks like this:

Browser
    ↓
http://localhost:8000
    ↓
Python http.server
    ↓
Project directory
    ↓
index.html
data/greetcards.csv
manifest.json
sw.js
icons/

The HTTP server simply provides these static files to the browser when the browser requests them.

Why Start the Server in the Project Root?

It is important to run the command from the directory that contains the files you want to serve.

Our project structure looks like this:

project/
    index.html
    data/
        greetcards.py
        greetcards.csv

Therefore, we open the terminal in project/ and run:

python -m http.server

Python treats the current directory as the root of the web server.

That means a browser request for:

http://localhost:8000/index.html

maps to:

project/index.html

and a request for:

http://localhost:8000/data/greetcards.csv

maps to:

project/data/greetcards.csv

This is exactly the directory structure that our JavaScript expects.

Relative URLs Now Make Sense

Our JavaScript uses a relative URL:

fetch("data/greetcards.csv")

Because the page is being served from:

http://localhost:8000/

the browser resolves the relative path as:

http://localhost:8000/data/greetcards.csv

The Python server receives that request and returns the CSV file.

This is one of the major reasons for using a local HTTP server during development. The same relative paths will later work when the application is deployed to a real web server.

Testing the CSV Request

Once the server is running, you can directly test the CSV file in the browser.

Open:

http://localhost:8000/data/greetcards.csv

The browser should be able to request the file from the local server.

This is a useful debugging technique. If the CSV file does not load here, the problem is probably related to the file path, project structure, server directory, or the file itself rather than the JavaScript filtering code.

Checking the Browser Console

The browser's developer tools are extremely useful during development.

If the application fails to load the CSV, open the developer tools and look at the Console and Network tabs.

The Console may show an error explaining why JavaScript failed. The Network tab allows you to see requests made by the page, including the request for greetcards.csv.

This gives us a much better debugging environment than simply opening an HTML file directly.

HTTP Is Enough for Development

Notice that our local server uses http://, not https://.

For basic development, that is perfectly fine. We mainly need an HTTP origin so that the browser treats the project like a normal web application and allows our static resources to be requested through normal web URLs.

We do not need to configure certificates or encryption for a server that exists only on our own computer.

Starting the Server on Another Port

If port 8000 is already being used by another program, Python allows us to specify a different port.

python -m http.server 8080

The application would then be available at:

http://localhost:8080

The port number is simply part of the local address. The rest of the project works in exactly the same way.

Stopping the Server

The Python server continues running until we stop it.

To stop it, assuming you are using GitBash on Windows or Linux Terminal, focus the terminal where the server is running and press:

Ctrl + C

The server will stop, and the browser will no longer be able to retrieve files from localhost:8000 until we start it again.

The Development Workflow

From now on, our normal development workflow will be very simple.

1. Open the project directory.
2. Start the Python HTTP server.
3. Open http://localhost:8000 in the browser.
4. Edit index.html.
5. Save the file.
6. Reload the browser.
7. Test the change.
8. Repeat.

The Python server does not need to be restarted every time we edit a file. It serves the files from the directory whenever the browser requests them.

Usually, saving a change and refreshing the page is enough to see the new version.

The Server Does Not Build the Application

It is important to understand what python -m http.server does not do.

It does not compile our JavaScript. It does not process our CSS. It does not run Python scraping code automatically. It does not create a database. It does not provide an application backend.

It is simply a small static file server.

When the browser requests a file, the server reads that file from disk and sends it back to the browser.

This is exactly what our project needs during development because the application itself is a static web application.

Development Server Versus Production Hosting

There is an important difference between our local development server and the final hosting environment.

During development we use:

http://localhost:8000

When the application is published, it will be hosted on GitHub Pages and accessed through HTTPS.

Our local Python server is therefore a development tool. It lets us reproduce the basic behavior of a real web server without requiring an internet connection or a hosting account.

Why GitHub Pages Matters for This Project

Our final application is made from static files. There is no backend that needs to execute Python or another server-side programming language when a user opens the application.

This makes static hosting a natural fit.

The files can be uploaded to a GitHub repository, and GitHub Pages can serve those files as a public website.

The resulting application will have a normal HTTPS address, which is important for some browser APIs used by our application.

Sharing Greeting Cards Requires More Than Local HTTP

One of the features of our application will be a Share button. On a mobile device, we want the user to be able to select an application such as WhatsApp or another installed sharing application from the operating system's share interface.

The JavaScript API involved is the Web Share API:

navigator.share({
    title: selectedCard.title,
    url: selectedCard.url
});

Browser security rules are important here. Features such as the Web Share API are intended to operate in secure contexts, which generally means HTTPS for a real deployed website, with special treatment for local development origins such as localhost.

Our local HTTP server is therefore useful for testing the application's basic behavior, loading the CSV, generating cards, opening the modal, and developing the interface. It should not be treated as the final environment for testing mobile sharing to applications such as WhatsApp.

Why We Cannot Fully Test WhatsApp Sharing Locally

Suppose the application is running at:

http://localhost:8000

This address only exists on the development computer. A phone cannot use that address to access the application in the same way that it can access a public website.

More importantly, the browser's security requirements for sharing and other powerful web APIs mean that the final sharing behavior should be tested from the deployed HTTPS version of the application.

Therefore, we should not spend time trying to make the local HTTP version behave exactly like the production version for every browser API.

Instead, we use the local server for normal development and perform the final sharing test after deploying the application to GitHub Pages.

Local Development and Production Testing

This gives us two different environments with different purposes.

Local development
http://localhost:8000
        ↓
Test HTML
Test CSS
Test JavaScript
Test CSV loading
Test filtering
Test modal
Test application behavior


GitHub Pages
https://...
        ↓
Test real public URL
Test PWA behavior
Test mobile sharing
Test sharing to apps such as WhatsApp

We do not need to wait until deployment to develop the entire application. Almost everything can be built and tested locally.

Deployment is simply the final environment check where features that depend on HTTPS and a public web origin can be tested properly.

Why Not Install a Larger Development Server?

There are many development servers available in the web-development ecosystem. We could use Node.js tools, Python web frameworks, IDE extensions, or a full application server.

None of that is necessary for this project.

Our application consists of static files, so Python's built-in server is enough. The command:

python -m http.server

gives us everything we need with no additional project configuration.

This also fits the philosophy of the project: use the simplest tool that solves the problem.

One Command Gives Us a Web Server

This is one of the convenient parts of Python for web development. A complete static file server is already included with Python.

There is no separate server source code that we need to write. We simply tell Python to run its HTTP server module:

python -m http.server

The -m option tells Python to run a module as a program. In this case, the module is http.server.

Python then starts the server and uses the current directory as the document root.

The Server Fits Our Project Architecture

Our architecture is now becoming very straightforward.

Python scraper
        ↓
data/greetcards.csv
        ↓
Static project files
        ↓
Python development HTTP server
        ↓
Browser
        ↓
HTML + CSS + JavaScript
        ↓
Greeting-card application

The scraper prepares the data, while the HTTP server simply makes the resulting files available to the browser.

There is no need to combine these two Python tasks. The scraper is run when we need to collect or refresh the dataset. The HTTP server runs while we are developing and testing the browser application.

A Typical Project Session

A normal development session might therefore look like this.

First, if the dataset needs to be refreshed, go into the data directory and run the scraper:

cd data
            python greetcards.py

Then return to the project root:

cd ..

Start the development server:

python -m http.server

Finally, open:

http://localhost:8000

From this point onward, development happens in the browser. We edit the HTML, CSS, and JavaScript, save the files, refresh the page, and inspect the result.

Why This Step Is Important

It may seem excessive to start a server for an application that consists of only a few files. In reality, this small step puts our development environment much closer to the environment in which the application will actually run.

The browser sees a normal HTTP origin. Relative URLs behave as expected. JavaScript can request the CSV file through HTTP. Static resources can be loaded using the same kind of paths that will later be used on GitHub Pages.

Most importantly, we avoid developing against file:// and then discovering later that browser security rules behave differently once the application is deployed.

Important: Use python -m http.server from the project root while developing. Do not open index.html by double-clicking it when you need to test JavaScript fetch() requests. The local server provides the HTTP environment that our application expects.

What We Have Now

Our project now has both a dataset and a proper way to serve the application during development.

The scraper creates data/greetcards.csv. The browser application will later use JavaScript to load that file. Python's built-in HTTP server provides the local HTTP environment needed for that request.

For local development, we use http://localhost:8000. For the final application, we will deploy the static files to GitHub Pages and use its HTTPS address.

The HTTPS deployment will also be important for testing features such as mobile sharing to applications like WhatsApp. We can develop almost everything locally, but the final sharing behavior should be tested from the deployed HTTPS version rather than treating the local development server as the production environment.

We now have the basic development environment ready. The next step is to start turning the empty HTML structure into the actual visual interface of the greeting-card application.
