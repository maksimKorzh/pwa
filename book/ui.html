Chapter 3

User Interface

Building the Interface Skeleton

Before we write any application logic, we need to decide what the user interface is going to look like. In our project, the interface is deliberately simple. We need a way to display categories, a way to request more cards, an area for the greeting cards themselves, and a simple window for viewing and sharing a selected card.

The HTML we are starting with is the actual skeleton of the application. At this stage, the CSS and JavaScript are intentionally empty. We will add the visual design and functionality later, but the complete structure of the interface can already be seen in the HTML.

This is an important way of thinking about web development. We do not have to build everything at once. First, we can describe the structure of the application using HTML. Then CSS can make that structure look good, and JavaScript can make it interactive.

HTML Is the Skeleton

HTML defines what exists in the application. CSS will control how those elements look, while JavaScript will control what they do.

The Complete HTML

Here is the complete HTML extracted from our project at this stage. The original application is written in Russian, but the version used in this book is translated into English. The structure is the same; only the user-facing text has been translated.

<!DOCTYPE html>
<html lang="en">
    <head>
        <meta charset="UTF-8">
        <meta name="viewport" content="width=device-width, initial-scale=1.0">
        <title>Greeting Cards</title>
        <style></style>
    </head>
    <body>
        <div class="sticky-controls">
            <button id="randomBtn"> 🎲 More Cards</button>
            <section id="categories"></section>
        </div>
        <section id="cards"></section>
        <div id="modal" class="hidden">
            <div class="modal-content">
                <img id="modalImg">
                <button id="shareBtn">Share</button>
                <button id="copyBtn">Copy Link</button>
                <button id="closeBtn">Close</button>
            </div>
        </div>
        <script></script>
    </body>
</html>

There is not much code here, and that is intentional. The application does not need a complicated interface. In fact, one of the interesting things about this project is how much functionality we can eventually get from such a small HTML structure.

The Document Type

The first line tells the browser that this is an HTML5 document:

<!DOCTYPE html>

This declaration is standard for modern HTML documents. It tells the browser to interpret the page using modern HTML standards rather than an older compatibility mode.

There is nothing application-specific about this line, but every normal HTML page should have it.

The HTML Element

The root of the entire document is the <html> element:

<html lang="en">

Everything else in the document is contained inside this element.

The lang attribute tells the browser that the primary language of the document is English in the translated version used in this book. The original application uses lang="ru" because its interface is Russian.

This is useful for browsers, search engines, accessibility software, and screen readers.

The application itself is not tied to a particular language. We are using English here so that the book is easier to follow, while the original application remains Russian.

The Head

The <head> contains information about the document that is not normally displayed as part of the main page content.

Our head contains the character encoding, viewport configuration, page title, PWA manifest, theme information, mobile-related metadata, and an empty style element where our CSS will eventually go.

It is worth looking at these pieces individually because several of them are particularly important for a PWA.

Character Encoding

First we specify UTF-8:

<meta charset="UTF-8">

UTF-8 allows the document to contain a very large range of characters and is the standard encoding we want to use for a modern web application.

This is particularly relevant to our project because the original application contains Russian text. The English version in this book uses translated interface text, but the underlying dataset remains Russian.

For example, the original application can write Russian button text directly in the HTML:

<button>Поделиться</button>

In the translated version used in the book, the same button is displayed as:

<button>Share</button>

We do not need to convert either language into special character codes.

The Mobile Viewport

The next line is extremely important for our mobile-first application:

<meta name="viewport" content="width=device-width, initial-scale=1.0">

The viewport is the visible area of the web page inside the browser. On a phone, we want our layout to use the actual width of the device screen.

The width=device-width part tells the browser to use the device's width as the width of the page.

The initial-scale=1.0 part tells the browser to display the page at its normal initial scale rather than starting with an unexpected zoom level.

Without this declaration, a mobile browser may use a wider virtual layout and then scale the result down. That can make a page designed for mobile behave in unexpected ways.

Mobile First

The viewport meta tag is one of the foundations of a mobile-friendly web application. It tells the browser that our layout should work with the actual dimensions of the user's device.

The Page Title

The title of our translated application is defined with:

<title>Greeting Cards</title>

This title can appear in browser tabs, bookmarks, browser history, and other places where the browser identifies the current page.

The original application uses the Russian title Открытки, which means greeting cards. We use Greeting Cards in the translated version of the book.

The Style Placeholder

At the end of the head we have an empty <style> element:

<style></style>

For now, it contains nothing.

Later, this is where we will place the CSS that controls the entire appearance of the application. We will define the background, buttons, card layout, spacing, modal window, typography, and mobile behavior here.

Keeping the style element in the document from the beginning also reinforces our single-file approach. We do not need a separate stylesheet for this small project.

The Body

Everything the user actually interacts with belongs inside the <body>.

Our body contains three main parts:

  • The controls and category area.
  • The greeting-card area.
  • The modal window used for a selected card.

These three parts correspond directly to the main things the user can do in our application.

The Sticky Controls

The first element in the body is:

<div class="sticky-controls">
    ...
</div>

The name sticky-controls describes the role we want this element to have. Later, CSS will make this section remain visible near the top of the screen while the user scrolls through greeting cards.

This is particularly useful on a phone. Imagine that the user has scrolled through ten greeting cards and suddenly wants to select another category. We do not want the user to scroll all the way back to the top just to find the category controls.

The HTML itself does not make the element sticky. The class simply gives us a convenient hook that CSS can use later.

The Random Button

Inside the controls we have our first button:

<button id="randomBtn"> 🎲 More Cards</button>

The button is intended to show another selection of greeting cards.

The visible text is written directly inside the button. We also use a dice emoji to make the purpose of the button immediately recognizable.

More importantly, the button has an id:

id="randomBtn"

This ID gives JavaScript a precise way to find the button later.

For example, JavaScript will eventually be able to do something like:

document.getElementById("randomBtn")

We are not writing that JavaScript yet. We are simply preparing the HTML so that the JavaScript will have something to connect to.

The Categories Section

Immediately below the random button is an empty section:

<section id="categories"></section>

This element is intentionally empty.

Why would we create an empty element?

Because the category buttons will be generated dynamically by JavaScript.

We do not want to manually write every category into the HTML. Instead, JavaScript will eventually have a list of categories and create the appropriate buttons automatically.

The empty section gives JavaScript a destination where those buttons can be inserted.

Empty Elements Can Be Useful

An empty HTML element is not necessarily unfinished HTML. It can be a deliberate container for content that will be generated dynamically by JavaScript.

The Cards Section

After the controls we have another empty section:

<section id="cards"></section>

This is the most important content container in the application.

It will eventually contain the greeting cards selected by the application.

Just like the categories section, it starts empty because we do not know in advance which cards the user will request. JavaScript will read the CSV dataset, search it, select the appropriate cards, and dynamically create the HTML needed to display them.

This means that the initial HTML does not need to contain hundreds or thousands of card elements.

Instead, we have a single container and let the application populate it when necessary.

Why Generate Cards Dynamically?

There is a major advantage to this approach.

Our greeting-card dataset can contain a large number of records, but the user only needs to see a small selection at any particular moment.

Loading every card into the HTML would make the document unnecessarily large and would make the page more difficult to manage.

Instead, the CSV becomes our data source and JavaScript decides what should currently be displayed.

The HTML therefore remains small regardless of how many greeting cards eventually exist in the dataset.

The Modal Window

The final major part of our interface is the modal:

<div id="modal" class="hidden">
    <div class="modal-content">
        ...
    </div>
</div>

A modal is an interface element that appears above the main page content and temporarily focuses the user's attention on a particular task.

In our application, the task is viewing and sharing a selected greeting card.

The modal has two important classes and IDs. The outer element has the ID modal and the class hidden. The inner element has the class modal-content.

The hidden class will initially make the modal invisible. Later, JavaScript will remove that class when the user selects a card.

The Modal Image

Inside the modal we have an image element:

<img id="modalImg">

Notice that there is no src attribute yet.

This is intentional because the application does not know which greeting card the user will select.

When the user clicks a card, JavaScript will take that card's image URL and assign it to the src property of this image.

The same modal can therefore be reused for every card in the application.

The Share Button

The first action button inside the modal is:

<button id="shareBtn">Share</button>

The purpose is straightforward: allow the user to share the selected greeting card using the sharing capabilities provided by the device and browser.

Again, the important detail at this stage is the ID:

id="shareBtn"

Later, JavaScript will use this ID to attach the sharing behavior to the button.

The Copy Button

The second action is:

<button id="copyBtn">Copy Link</button>

This gives the user another way to use the selected card. Instead of opening the system sharing interface, the user can copy the image URL to the clipboard.

This is useful because not every browser or device provides exactly the same sharing capabilities. Having both sharing and copying gives the user another simple way to send the card to someone.

The Close Button

Finally, the modal contains:

<button id="closeBtn">Close</button>

This button will close the modal and return the user to the card list.

Like the other buttons, its ID gives JavaScript a way to attach the required behavior later.

The Script Placeholder

At the bottom of the body we have another empty element:

<script></script>

This is where our JavaScript will eventually live.

Putting the script at the end of the body is convenient for this small application because the HTML elements already exist in the document when the JavaScript is executed.

We will eventually use this script to load the CSV file, create category buttons, filter cards, display random cards, open and close the modal, and implement sharing and clipboard functionality.

One HTML File

At this point, it is worth stepping back and looking at what we have created.

We have not installed a framework. We have not created a React project. We have not added a build system. We have not created a backend. We have not even written any CSS or JavaScript yet.

We have simply created one HTML file containing the complete interface structure.

This is one of the reasons I like building small PWAs this way. There is very little hidden machinery. If you open index.html, you can see the application.

The essential structure is all there: the page metadata, controls, categories, cards, modal, and placeholders for CSS and JavaScript.

Classes and IDs

You may have noticed that the HTML uses both class and id attributes.

They serve different purposes in our project.

Classes are primarily useful for describing groups of elements and applying common CSS rules. For example, modal-content describes the visual container inside our modal.

IDs identify individual elements that JavaScript needs to access directly. For example, randomBtn identifies the random-card button, while modalImg identifies the image displayed inside the modal.

This separation is not an absolute rule — CSS can use IDs and JavaScript can work with classes — but using meaningful classes for styling and unique IDs for important application elements makes the code easier to understand.

HTML as an API for Our JavaScript

The IDs and classes we define now become connection points for the code we will write later. The HTML provides the structure, while JavaScript will use those named elements to control the application.

The Interface We Need

Our entire application can therefore be reduced to a surprisingly small collection of interface elements.

  • A top control area that remains available while browsing.
  • A button for requesting another selection of cards.
  • A dynamically generated list of categories.
  • A dynamically generated list of greeting cards.
  • A modal for viewing a selected card.
  • A sharing button.
  • A copy-link button.
  • A close button.

That is essentially the whole user interface.

The interesting part is what happens next. None of these elements knows where the greeting cards come from yet. The categories do not exist yet. The cards do not exist yet. The modal does not know which image to display.

All of that information will come from the application logic.

From Static HTML to an Application

Our current HTML is therefore not the finished application. It is the foundation on which the application will be built.

CSS will transform the basic elements into a mobile-friendly interface. We will create the sticky controls, category buttons, card layout, modal, spacing, typography, and visual appearance.

JavaScript will then bring the interface to life. It will load our CSV dataset, search the data, generate the appropriate HTML, respond to button clicks, open the selected card, and provide sharing and clipboard functionality.

But the important thing is that we already know what the final application needs to contain.

We are not going to keep adding random interface elements as we develop. The skeleton gives us a clear structure from the beginning.

This is also what makes the single-file approach practical. The entire user interface can remain in one place, the CSS can remain in the same document, and the JavaScript can remain there as well. The result is a small and portable application that can be opened, understood, copied, and modified without first learning a complicated project structure.

The Complete Loop

The Complete Interface Loop

HTML creates the interface skeleton → CSS makes it look like an application → JavaScript loads the data → JavaScript fills the categories and cards → user selects a card → modal displays the card → user shares or copies it → modal closes → user continues browsing.

That is the basic architecture of our user interface. The rest of the project is about filling in these placeholders one by one without making the underlying structure unnecessarily complicated.
